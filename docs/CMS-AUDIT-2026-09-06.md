## Simulator integration and limits

The new interface follows the five-tab calculator supplied by the client:
<https://simulation-portage-salarial.fr/sources/6535194A4DB03/simulator>.
It sends anonymous numeric inputs to the same public MULA calculation endpoints
used by that source's official JavaScript component. It does not use the former
flat social-charge estimate and does not submit contact details to MULA.

The default management fee is **5%, locked**. Admin settings control the website
interface and the fee/expense/day/contract values sent to each calculation.
Payroll contribution rates, thresholds, source service availability and
source-level result restrictions remain in the MULA account. MULA's
[integration description](https://simulation-portage-salarial.fr/demo) explains
its source configuration and payroll-rule maintenance. Those internals cannot
be changed from our CMS without MULA account/API access.

The public API was observed in the vendor's current component; it is an external
dependency, not a versioned integration contract supplied by MULA. Failed,
incomplete or timed-out responses produce an error, never an invented estimate.
The source can also suppress results. Local hidden/locked controls are visitor
interface settings, not a security boundary for the third-party public API.

Validation used the actual source on 6 September:

- All five modes returned successful calculation responses.
- TJM €500 × 20 days: changing management fees from 8% to 5% changed the returned
  fee from €800 to €500 and net before withholding from €4,811.66 to €4,910.28.
- The source permits browser CORS requests from the local site.
- PDF download returned a valid `application/pdf` document with a `%PDF` signature.
- For revenue/total-cost inputs, MULA's returned `tjm` field echoed a monthly
  amount. The displayed daily rate is derived from returned monthly revenue
  divided by submitted days, without altering the engine's salary amounts.

## Remaining issues for the next CMS pass

1. **Demo screens still resemble operational tools.** Admin team permissions,
   internal notifications, calendar and several reporting/lead screens import
   `admin-demo.data.ts`. Some buttons only change local state or are disabled.
   They need real tables, policies and actions or clear demo labeling. The public
   team editor and site notifications added here are separate, live CMS controls.
2. **General Settings contains obsolete simulator values.** Its disabled fields
   still read the demonstration formula. `/admin/calculator` is now authoritative
   for the new public simulator. Remove that duplicate display in the next pass.
3. **Opening the visual editor can publish missing fallback blocks.**
   `createMissingVisibleBlocks()` calls `cms_create_content_block`, which publishes
   version 1. Registration and publication should become separate operations.
4. **Most content keys still depend on DOM positions.** Reordering other sections
   needs the same key audit performed here. Gradually replace positional keys
   with stable semantic keys, preserving all existing published values.
5. **Saving settings is not one atomic server operation.** The new panels check
   `updated_at` and reject known stale edits, but a concurrent edit between that
   check and save/publish remains possible. Add an atomic compare-and-publish RPC.
6. **Roster and notifications share the CMS's 10,000-character document limit.**
   Validation prevents oversized publication. For a larger team, use a dedicated
   member table and ordering field, rather than one JSON document. Uploaded
   portraits are intentionally immutable; a later cleanup tool must retain media
   referenced by historical versions.
7. **Visual text editing does not administer every asset or link destination.**
   Big Porters copy/badges are editable. A general-purpose image/link editor and
   responsive layout controls require their own schema and UI; the new roster
   uploader only covers team portraits.
8. **Database rollout and website deployment need an explicit status display.**
   The UI should distinguish a connected public client, authenticated publishing,
   storage availability and the deployed code version.
